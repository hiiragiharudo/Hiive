# SkillRoute-Bench 标注指南

> 版本 v0 ｜ 对应数据集 `eval/bench/skillroute-bench-v0.jsonl`
>
> **本指南的存在本身就是一项研究发现**：开发期探针集由单人标注，暴露了
> 「不可满足的查询」与「只按技能名标注导致漏标中文技能」两类错误
> （见技术设计文档 §6.7）。正式基准必须有**公开的、可执行的**标注规则，
> 否则任何基于它的结论都不可信。

---

## 1. 评测对象与边界

**本基准评测的是"技能调度"，不是"渗透能力"。**

| | 评测单位 | 回答的问题 |
|---|---|---|
| 本基准 | **技能** | 该给 Agent 看哪些技能？ |
| AutoPenBench / Cybench / TSecBench 等 | **任务** / **Agent** | 目标打进去了吗？ |

二者正交。本基准**不声称**替代既有基准，也不评测漏洞发现能力。

---

## 2. 字段定义与标注规则

| 字段 | 类型 | 规则 |
|---|---|---|
| `id` | str | `{lang}-{topic}-{序号}`；弃权用例用 `abstain-{序号}` |
| `query` | str | 用户口吻的任务描述。**不得直接抄技能的 `name` 或 `description`**（见 §4 循环性控制） |
| `expected` | list[str] | **期望被召回的技能名**。必须逐字使用语料中真实存在的技能名 |
| `acceptable` | list[str] | 可接受的替代答案。不计入主指标，仅用于失效分析 |
| `lang` | zh/en | 查询语言。中英配比用于分层量化跨语言鸿沟 |
| `domains` | list[str] | 覆盖的安全域标签，用于分层报告 |
| `source` | hand / body-derived / report-derived | **循环性控制的关键字段** |
| `confidence` | high / medium / low | 标注置信度。低置信度条目应在分层报告中单列 |
| `notes` | str | 标注理由；**弃权用例必须写明"为什么库中无正确答案"** |

### 2.1 `expected` 的判定规则（核心）

一条技能 A 应被判为"期望"，当且仅当满足以下**任一条**：

1. **直接对应**：A 的主题与查询描述的任务一一对应（如"报错注入"↔`sqli-sql-injection`）；
2. **必经环节**：完成该任务**必须**使用 A 描述的方法论，即使查询未点名该技术；
3. **唯一可行入口**：语料中只有 A 覆盖该主题。

**不构成"期望"的情形**：

- A 只是**领域相关**但非本任务所需（如查询讲"上传"，`file-agent` 若只是泛泛的文件类
  漏洞总览，则列入 `acceptable` 而非 `expected`）；
- A 是**伞状技能**（如 `src-6k-skill`、`pent3st`）——它们覆盖所有主题，
  因此与任何查询都"相关"，**不得作为 `expected`**。若路由器只召回伞状技能，
  应判为**未命中**，而非"命中但不够精确"。
- A 与查询主题**部分重叠但会误导执行**（如"清理日志"↔`traffic-analysis-pcap`）。

### 2.2 多答案情形的处理

一个查询常有多个合理答案。规则：

- 全部写入 `expected`（**任一命中即算命中**，判定用"片段包含"）；
- 若某答案的正确性存在争议，降为 `acceptable` 并降低 `confidence`；
- `expected` 中**不得**放入"只要沾边就算对"的宽泛技能——这会虚高指标。

### 2.3 弃权用例（`expected: []`）的标注规则

弃权用例用于测量**路由器是否会硬凑答案**，是本基准的特色指标。

合格条件（须同时满足）：

1. **技能库中确实没有对应技能**——标注时须实际检索确认；
2. 最好具备**近义陷阱**特征：字面含安全术语但意图不是安全测试。
   例："MySQL 慢查询怎么优化"（含 MySQL，但属性能优化）、
   "用 Nginx 配反向代理"（含 Nginx，但属运维配置）、
   "how do I rename a git branch"（含 git，但属日常操作）。

**不合格**：纯随机字符串（如 `zzzz qqqq`）。这类查询靠词面检索自然返回空，
**不构成对弃权能力的测试**。必须是"看起来相关但其实不该路由"的查询。

## 3. 指标定义

| 指标 | 定义 | 说明 |
|---|---|---|
| Recall@k | `expected` 任一技能出现在 top-k 的条目比例 | 分母**不含**弃权用例 |
| MRR | 期望技能在**阶段一完整排序**中名次的倒数均值 | 用完整排序而非 top-k，故不受 k 截断影响 |
| 弃权准确率 | 弃权用例中正确返回空结果的条目比例 | 衡量"不硬凑"的能力 |
| 误路由率 | `1 − 弃权准确率` | |
| 元数据节省 | 相对全量注入技能元数据的 token 节省比例 | 见技术设计文档 §5 的成本模型 |

**分层报告是强制要求**：必须按 `source` 分层（`hand` 与 `body-derived` 分开），
并按 `lang` 与 `confidence` 分层。混合报告会掩盖循环性与标注质量问题。

---

## 4. 循环性控制（本基准最关键的方法学要求）

**风险**：若查询由技能 A 的 `description` 生成，则词面检索器必然命中 A，
指标被虚高——测的是"能否复述描述"，不是"能否路由"。

**控制措施**：

1. `source` 字段显式记录构造方式，**指标必须分层报告**；
2. `body-derived` 查询的生成**必须排除 `name` 与 `description` 的词元**，
   只允许使用技能**正文**的操作性词汇；
3. 生成后须**人工复核并改写**，去除与原文重合的措辞；
4. **主指标只以 `hand` 子集为准**。`body-derived` 子集仅用于扩大样本、
   观察趋势，**不得作为主要结论依据**。

---

## 5. 已知局限（必须写入论文）

1. **规模小**：v0 共 86 条（计分 76 + 弃权 10），不足以支撑精细的统计推断。
2. **单人标注**：无第二标注者，故无标注者间一致性（inter-annotator agreement）
   数据。**这是 v0 最大的方法学弱点**，后续须邀请他人复标一个子集并报告
   Cohen's κ。
3. **判定用"片段包含"**：为容忍技能命名差异而放宽，但也会把
   `sqli-sql-injection` 与 `nosql-injection` 这类名字部分重叠的技能混淆。
4. **中文查询占多数**（69/86），英文样本偏少，英文侧的结论置信度较低。
5. **弃权用例仅 10 条**，弃权准确率的粒度粗（每条 0.1）。
