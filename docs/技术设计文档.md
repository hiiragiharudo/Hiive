## 1. 设计目标与约束

| # | 目标 | 设计后果 |
|---|---|---|
| G1 | 技能调度成本不随技能库规模线性增长 | 两阶段架构：检索索引常驻内存，**不进 prompt**；仅注入 top-k |
| G2 | 研究核心可离线复现 | 技能引擎**零第三方依赖**（纯标准库）；LSA 通道可选依赖 numpy |
| G3 | 决策链路完全可控 | 自研 Agent 循环，不依赖 LangGraph 等重型框架 |
| G4 | 结论可信、可比 | 内置 baseline 对照与消融开关（分词策略 / 检索通道 / 分字段 / k 值） |
| G5 | 演示直观 | 路由结果携带「召回依据」字段得分，供前端直接渲染 |

**非目标**（明确划出，避免落入红海）：不重造工具封装（复用 MCP）、不重造多 Agent 分工框架、
不做通用漏洞扫描器。

## 2. 总体架构

```
┌──────────────────────────────────────────────────────────────────┐
│  前端控制台  Next.js + React + TS                                  │
│  技能库管理 │ 检索路由可视化 │ 任务执行 │ 评测看板 │ 证据与报告      │
└───────────────────────────┬──────────────────────────────────────┘
                            │ REST + SSE
┌───────────────────────────▼──────────────────────────────────────┐
│  后端  Python 3.12+ / FastAPI                                     │
│                                                                   │
│  ┌────────────────┐   ┌──────────────────────────────────────┐   │
│  │ 技能引擎        │   │ Agent 执行引擎（待实现）              │   │
│  │ ★两阶段路由器   │──▶│ 循环 / 上下文管理 / 终止判定          │   │
│  │  注册表 索引    │   └──────────────┬───────────────────────┘   │
│  └────────────────┘                  │                            │
│  ┌────────────────┐   ┌──────────────▼───────────────────────┐   │
│  │ 评测引擎（待实现）│  │ 工具层：MCP 客户端（可选接入）        │   │
│  │ SkillRoute-Bench│  └──────────────────────────────────────┘   │
│  └────────────────┘                                              │
└──────────────────────────────────────────────────────────────────┘
        │                    │                     │
   PostgreSQL            检索索引              文件系统
   （待实现）        （内存：BM25 + 向量）     （技能语料/证据）
```

**关键设计决策：检索索引常驻内存而非向量数据库。**
语料规模为百级技能条目，索引可完全驻留内存，查询延迟在毫秒级（实测 stage1 ≈ 5 ms）。
引入向量数据库会带来部署复杂度而无收益；论文中亦可将"何时必须外置索引"作为规模扩展的讨论点。

## 3. 技能包规范

### 3.1 兼容 agentskills.io 的最小集

```yaml
---
name: idor-hunt                    # 必填
description: >-                    # 必填，规范要求 ≤1024 字符
  测试水平越权（IDOR）时调用该技能：替换对象标识，比较不同主体返回的数据归属。
---
# 正文（Markdown，渐进披露）
```

### 3.2 本课题扩展的路由元数据

**实测依据**：本机 135 个技能条目中，**125/125 完全没有**
`triggers` / `phase` / `domains`——它们只有 `name` + `description`。
这意味着「路由元数据」在本课题中**必须被生成**，而不是被消费。

| 字段 | 类型 | 作用 | 是否进上下文 |
|---|---|---|---|
| `domains` | list[str] | 安全域（web/api/ad/cloud/mobile/ai…） | ✗ 仅进索引 |
| `phase` | str | 渗透阶段 `recon`/`discovery`/`exploitation`/`post`/`report` | ✗ |
| `targets` | list[str] | 适用目标（wordpress/spring/graphql…） | ✗ |
| `triggers` | list[str] | 典型触发语 | ✗ |
| `requires` | list[str] | 前置技能（构成依赖图） | ✗ |
| `provides` | list[str] | 产出的状态（供编排使用） | ✗ |
| `tools` | list[str] | 所需工具 | ✗ |
| `risk` | str | `low`/`medium`/`high`（决定是否需要审批） | ✗ |

**关键性质：所有扩展元数据只存在于检索索引中，不进入 prompt。**
因此扩展元数据不会带来任何上下文成本——这正是两阶段架构带来的自由度：
传统"全量注入"范式下，加字段就等于加 token；本架构下加字段只加索引维度。

## 4. 技能引擎设计

### 4.1 模块划分

| 模块 | 职责 | 依赖 |
|---|---|---|
| `models.py` | `SkillMeta` / `Skill` / `RouteCandidate` / `RouteResult`，成本模型 | 标准库 |
| `parser.py` | `SKILL.md` 解析 + 元数据校验 | 标准库 |
| `tokenize.py` | 中英混合分词（3 种策略，供消融） | 标准库 |
| `bm25.py` | BM25 Okapi 检索通道 | 标准库 |
| `vectors.py` | TF-IDF 稀疏向量 + LSA 潜在语义 | 标准库（LSA 需 numpy） |
| `fusion.py` | RRF 多通道融合 | 标准库 |
| `registry.py` | 加载 / 校验 / 建索引 / 分字段检索 | 上述 |
| `router.py` | ★两阶段路由 + 依赖闭包编排 | 上述 |

### 4.2 分词策略（`tokenize.py`）

不引入 jieba。理由：① 额外依赖削弱可复现性；② 通用词典对安全术语切分不佳
（`越权`、`反序列化`、`Kerberoasting`）；③ 领域词典维护成本高。

**方案**：ASCII 词 + CJK 单字 + CJK 相邻二元组。

```
"水平越权 IDOR 测试"  →  ["水平","越权","idor","测","试","测试","平越","平","越","权"]
```

字符 bigram 在中文检索上效果接近分词，且天然覆盖未登录词与领域术语。
三种策略可切换（`hybrid` / `ascii_only` / `bigram_only`）作为消融自变量。

### 4.3 BM25 通道：分字段加权（`registry.py`）

**实测发现的缺陷**：把技能的全部字段拼成一段文本再做 BM25 会产生**文档长度偏置**。
本机语料中，5 个"伞状技能"（`src-6k-skill`、`pent3st`、`cve-yu2`、`secknowledge-skill`、
`vibe-pentest`）的 `description` 是数百字的中文长段落，而 103 个细粒度子技能的描述简短。
拼接式索引下，前者因词频累积几乎垄断 top-5。

**方案**：每个字段独立建 BM25 索引，逐字段**最大值归一化**后按权重求和。

```
score(d, q) = Σ_f  w_f · ( bm25_f(d, q) / max_d' bm25_f(d', q) )
```

归一化是必要的：不同字段的 IDF 量级不可比（`name` 字段的 IDF 天然远高于 `description`）。

| 字段 | 权重 |
|---|---:|
| `name` | 3.0 |
| `triggers` | 3.0 |
| `targets` | 2.0 |
| `description` | 1.0 |
| `domains` | 1.0 |
| `tools` | 1.0 |

保留拼接式索引（`scoring="flat"`）作为消融基线。

### 4.4 向量通道（`vectors.py`）

不使用 sentence-transformers / torch（Python 3.14 下无稳定轮子，且损害可复现性）。
采用两级：

1. **TF-IDF 稀疏向量**：sublinear tf + L2 归一化。与 BM25 的差异在于长度归一化方式，
   对短技能描述更公平。纯标准库。
2. **LSA 潜在语义**：TF-IDF 矩阵上做截断 SVD（`X ≈ UΣVᵀ`），文档向量取 `UΣ`，
   查询投影 `qᵀVΣ⁻¹`。可捕捉词面不重合的语义相近。仅需 numpy，百级文档下秒级完成。

神经嵌入模型可通过 `Embedder` 协议接入，作为消融的第四个通道，**但不是必需依赖**。

### 4.5 融合（`fusion.py`）

RRF（Cormack et al., SIGIR 2009）：`RRF(d) = Σ_c 1/(k + rank_c(d))`，`k=60`。

选 RRF 而非加权分数求和：BM25 得分无上界、余弦在 [-1,1]，量纲不可比，
归一化方式本身又是一个待调参的自由度。RRF 只用排名，无需归一化与调参。

### 4.6 ★两阶段路由器（`router.py`）

```
阶段一（召回，不注入上下文）
  查询 + 可选渗透阶段
    ├─ 分字段 BM25 ──┐
    └─ 向量通道  ────┴─▶ RRF 融合 ─▶ top-recall_n
                                       │
阶段二（按需加载）                      ▼
  仅注入 top-k 技能的元数据 + 正文 ─▶ Agent
```

**阶段先验**：若给定当前渗透阶段，与该阶段一致的技能获得 `phase_bonus` 加权奖励
（默认 0.004，可关闭），实现"分阶段动态路由"——侦察阶段完成后的技能集与
利用阶段不同，静态路由无法应对。

**依赖编排**：`dependency_closure()` 按 `requires` 展开拓扑序，并检测循环依赖。

**可解释性**：每个候选携带 `matched_fields` 与分字段归一化得分，前端直接渲染
"为什么召回这个技能"。实测输出形如 `命中 描述(1.00)`。

## 5. 成本模型（诚实版）

**朴素比较是错的。** 若直接比较「全量注入全部技能」与「只注入 top-k 正文」，
会得出**负节省**——因为真实技能正文长达数百行，5 个正文的开销远超 135 条元数据。
实测：该错误模型下 `token_saving_ratio = −0.99`。

**正确模型**：把成本拆为两项，并在**同等 k** 下对照（即假设基线也恰好选中同样
k 个技能——这对基线最有利，因而是保守比较）：

| 方案 | 元数据项 | 正文项 |
|---|---|---|
| 基线（agentskills.io 全量注入） | `N × meta` | `k × body` |
| 本课题（两阶段路由） | `k × meta` | `k × body` |

节省量恰为 **`(N − k) × meta`**，随技能库规模 `N` **线性增长**。
所以正确的论点是"**元数据开销从 O(N) 降到 O(k)**"，
而**不是**"总 token 一定更少"。

**实测（本机 125 个技能，查询「WordPress 管理员登录入口」，k=5）**：

| 项 | 基线 | 本课题 |
|---|---:|---:|
| 元数据 | 20,895 | 1,611 |
| 正文 | 40,038 | 40,038 |
| **合计** | **60,933** | **41,649** |
| 元数据项节省 | — | **92.3%** |
| 总开销节省 | — | 31.6% |

token 数由字符数按 1.6 字符/token 估算（中英混合语料经验系数），
**论文中须标注为估算方法**，正式实验应改用真实 tokenizer 计量。

## 6. 实测发现（截至当前语料）

> 可用 `backend/tools/probe_routing.py` 完整复现。

### 6.1 发现一：路由元数据完全缺失

`125/125` 个技能没有 `triggers`/`phase`/`domains`。它们只有 `name` + `description`。
**这直接证实了开题报告研究内容一的必要性——路由元数据必须被生成。**

### 6.2 发现二：中英跨语言路由鸿沟（核心问题）

本机语料是**双语异质**的：

| 技能群 | 数量 | 描述语言 | 举例 |
|---|---:|---|---|
| 伞状技能 | 5 | **中文长段落** | `src-6k-skill`、`pent3st`、`secknowledge-skill` |
| 细粒度子技能 | 103 | **英文** | `active-directory-kerberos-attacks`（"Use when targeting AD authentication via AS-REP roasting, Kerberoasting…"） |

探针实测（9 条查询，5 个期望技能片段）：

| 查询语言 | 命中期望技能 |
|---|---|
| **英文** | **3 / 3** |
| **中文** | **2 / 6** |

中文查询失败时，中文长描述的伞状技能几乎垄断 top-5；而中文的字面 token
**根本无法命中英文描述**。这不是实现缺陷，而是词面检索在双语异质语料上的固有失效模式。

**这是本课题最有价值的问题发现**，对应解法（待实现）：

1. **双语领域词典 + 查询扩展**：`越权 → BOLA/IDOR/authorization`、`后台 → admin panel`、
   `票据 → Kerberos ticket`、`域 → Active Directory`。离线、无 LLM 依赖。
2. **词典来源可自动化**：从技能 `name`/`description` 与 1610 份真实 SRC 报告中
   挖掘中英术语共现对，而非纯人工编写。

### 6.3 发现三：文档长度偏置

见 §4.3。已通过分字段 BM25 缓解。**效果须在 SkillRoute-Bench 上量化**（待实现）。

### 6.4 发现四：技能库存在同名冲突

8 组同名技能，全部是 `vibe-pentest/references/pentest_skills/` 中
**vendored 复制的 `hack-skills` 子技能**。注册表按 `name` 去重并**记录冲突而非静默覆盖**
（`LoadReport.duplicates`），保留先出现的 `hack-skills` 原件。

### 6.5 发现五：含中文的"无关"查询不会返回空结果

字符 bigram 会在词面上产生偶然重叠（如「内容」命中技能描述）。
这是词面检索的固有特性，不是缺陷——**真正的路由质量必须靠带标注真值的
SkillRoute-Bench 度量**，不能靠"看起来对不对"。

## 7. Agent 执行引擎设计（待实现）

### 7.1 执行循环

```
观察攻击图状态
  → 技能路由（两阶段，带 phase 先验）
  → 依赖编排（dependency_closure 补前置技能）
  → 工具调用（MCP）
  → 证据落盘（原始请求/响应）
  → 验证判据判定（Verifier 独立复核）
  → 更新攻击图
  → 终止判定（步数上限 / 状态无变化检测 / 目标达成）
```

### 7.2 角色分工

| 角色 | 职责 | 对应实现要点 |
|---|---|---|
| Orchestrator | 规划、技能路由、维护攻击图与队列 | 复用 `SkillRouter` |
| Executor | 执行技能操作序列、采集证据 | MCP 客户端 + 证据存储 |
| Verifier | **独立复核**发现，抑制误报 | 验证判据执行器（见下） |
| Reporter | 汇总结构化报告 | 模板 + 证据引用 |

### 7.3 验证判据（抑制误报的关键）

每个技能可在 frontmatter 声明 `verify:` 块，描述"什么算成功"。设计为**受限 DSL**，
仅允许可在沙箱中自动执行的操作子集：

```yaml
verify:
  - kind: http_diff            # 发送两个请求比较响应差异
    a: {method: GET, path: "/api/order/{id_a}"}
    b: {method: GET, path: "/api/order/{id_b}"}
    assert: both_200_and_different_owner
  - kind: status_change        # 未授权访问的判定
    request: {method: GET, path: "/admin/users"}
    assert: status_not_in: [401, 403]
```

**只有通过验证判据的候选才能升级为"发现"**，且必须附带可复现证据。

### 7.4 约束机制

- **作用域强制**：所有出站请求经统一出口，目标须在授权资产清单内，越界拒绝并告警；
- **风险审批**：`risk: high` 的技能默认挂起，需人在环路批准；
- **请求节流**：按目标维度限速；
- **攻击图收敛**：决策空间限定为"在攻击图上选择技能"，不在图上的资产不可达。

## 8. 评测闭环设计

### 8.1 SkillRoute-Bench（路由质量基准）

| 组成 | 设计 |
|---|---|
| 任务描述集 | 200+ 条，覆盖 16 个安全域；中英各半（用于量化跨语言鸿沟） |
| 真值标注 | 每条标注"应召回的技能集合"+ 标注置信度；公开标注指南 |
| 指标 | Recall@k、MRR、误路由率、token 成本、查询延迟 |
| Baseline | ① 全量注入 ② 纯关键词 ③ 纯向量 ④ 朴素 LLM 选择 ⑤ 拼接式 BM25 |

**真值来源**：专业技能判断 + 1610 份真实 SRC 报告中的任务描述（脱敏）。
**可行性优势**：路由评测**完全离线**，不需要调用 LLM，零 API 成本。

### 8.2 端到端评测

- 靶场：Docker 化 DVWA / OWASP Juice Shop / WebGoat（**指定版本 + 锁定镜像 digest**）
- 指标：任务成功率、漏洞**精确率/召回率/F1**、无效动作占比、token 与时间成本
- **可复现性规范**：重复 5 次报告方差与置信区间；披露模型版本/温度/工具版本/镜像 digest/系统提示全文
- **负样本实验**：明确报告失败任务及原因

### 8.3 消融实验矩阵

| 自变量 | 取值 | 验证的假设 |
|---|---|---|
| 分词策略 | hybrid / ascii_only / bigram_only | CJK bigram 的贡献 |
| 检索通道 | bm25 / vector / 双通道 | 混合检索的增益 |
| BM25 建索引方式 | fielded / flat | **分字段设计消除长度偏置的贡献** |
| LSA 维度 | 16 / 32 / 64 / 128 | 潜在语义的增益与最优维度 |
| top_k | 1 / 3 / 5 / 10 | 成功率-成本权衡曲线 |
| phase 先验 | 开 / 关 | 分阶段动态路由的贡献 |
| 查询扩展 | 开 / 关 | **跨语言鸿沟的修复效果** |
| 技能库规模 | 25 / 50 / 125 / 250 / 500 | **核心卖点：成本-成功率曲线** |

## 9. 数据模型（待实现）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `skills` | name(PK), description, domains, phase, targets, triggers, risk, source, body_path | 技能库（正文存文件系统） |
| `skill_deps` | skill_name, requires_name | 依赖边（可查询闭包） |
| `tasks` | id, title, target_scope, state_phase, status | 任务 |
| `task_skills` | task_id, skill_name, stage, score, reason, injected_tokens | **路由留痕**（论文数据来源） |
| `assets` | id, task_id, kind(domain/ip/service/endpoint), value, tested | 攻击图节点 |
| `findings` | id, task_id, skill_name, kind, severity, verified, evidence_ref | 发现（`verified` 由 Verifier 置位） |
| `evidence` | id, finding_id, kind(http/screenshot), raw_ref, ts | 证据链 |
| `eval_runs` | id, bench_version, config_json, metrics_json, started_at | 评测运行 |
| `eval_labels` | query_id, query_text, expected_skills, confidence | 基准真值 |

`task_skills` 表是论文实验数据的直接来源——它记录了每次路由的候选、得分、
注入 token 与依据，可用于事后分析路由质量与成本。
