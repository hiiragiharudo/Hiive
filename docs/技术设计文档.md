## 1. 设计目标与约束

| # | 目标 | 设计后果 |
|---|---|---|
| G1 | 技能调度成本不随技能库规模线性增长 | 两阶段架构：检索索引常驻内存，**不进 prompt**；仅注入 top-k |
| G2 | 研究核心可离线复现 | 技能引擎**零第三方依赖**（纯标准库）；LSA 通道可选依赖 numpy |
| G3 | 决策链路完全可控 | 自研 Agent 循环，不依赖 LangGraph 等重型框架 |
| G4 | 结论可信、可比 | 内置 baseline 对照与消融开关（分词策略 / 检索通道 / 分字段 / k 值） |
| G5 | 演示直观 | 路由结果携带「召回依据」字段得分，供前端直接渲染 |

**非目标**（明确划出，避免落入红海）：不重造工具封装（复用 MCP）、不重造多 Agent 分工框架、
不做通用漏洞扫描器。

## 2. 总体架构

```
┌──────────────────────────────────────────────────────────────────┐
│  前端控制台  Next.js + React + TS                                  │
│  技能库管理 │ 检索路由可视化 │ 任务执行 │ 评测看板 │ 证据与报告      │
└───────────────────────────┬──────────────────────────────────────┘
                            │ REST + SSE
┌───────────────────────────▼──────────────────────────────────────┐
│  后端  Python 3.12+ / FastAPI                                     │
│                                                                   │
│  ┌────────────────┐   ┌──────────────────────────────────────┐   │
│  │ 技能引擎        │   │ Agent 执行引擎（待实现）              │   │
│  │ ★两阶段路由器   │──▶│ 循环 / 上下文管理 / 终止判定          │   │
│  │  注册表 索引    │   └──────────────┬───────────────────────┘   │
│  └────────────────┘                  │                            │
│  ┌────────────────┐   ┌──────────────▼───────────────────────┐   │
│  │ 评测引擎（待实现）│  │ 工具层：MCP 客户端（可选接入）        │   │
│  │ SkillRoute-Bench│  └──────────────────────────────────────┘   │
│  └────────────────┘                                              │
└──────────────────────────────────────────────────────────────────┘
        │                    │                     │
   PostgreSQL            检索索引              文件系统
   （待实现）        （内存：BM25 + 向量）     （技能语料/证据）
```

**关键设计决策：检索索引常驻内存而非向量数据库。**
语料规模为百级技能条目，索引可完全驻留内存，查询延迟在毫秒级（实测 stage1 ≈ 5 ms）。
引入向量数据库会带来部署复杂度而无收益；论文中亦可将"何时必须外置索引"作为规模扩展的讨论点。

## 3. 技能包规范

### 3.1 兼容 agentskills.io 的最小集

```yaml
---
name: idor-hunt                    # 必填
description: >-                    # 必填，规范要求 ≤1024 字符
  测试水平越权（IDOR）时调用该技能：替换对象标识，比较不同主体返回的数据归属。
---
# 正文（Markdown，渐进披露）
```

### 3.2 本课题扩展的路由元数据

**实测依据**：本机 135 个技能条目中，**125/125 完全没有**
`triggers` / `phase` / `domains`——它们只有 `name` + `description`。
这意味着「路由元数据」在本课题中**必须被生成**，而不是被消费。

| 字段 | 类型 | 作用 | 是否进上下文 |
|---|---|---|---|
| `domains` | list[str] | 安全域（web/api/ad/cloud/mobile/ai…） | ✗ 仅进索引 |
| `phase` | str | 渗透阶段 `recon`/`discovery`/`exploitation`/`post`/`report` | ✗ |
| `targets` | list[str] | 适用目标（wordpress/spring/graphql…） | ✗ |
| `triggers` | list[str] | 典型触发语 | ✗ |
| `requires` | list[str] | 前置技能（构成依赖图） | ✗ |
| `provides` | list[str] | 产出的状态（供编排使用） | ✗ |
| `tools` | list[str] | 所需工具 | ✗ |
| `risk` | str | `low`/`medium`/`high`（决定是否需要审批） | ✗ |

**关键性质：所有扩展元数据只存在于检索索引中，不进入 prompt。**
因此扩展元数据不会带来任何上下文成本——这正是两阶段架构带来的自由度：
传统"全量注入"范式下，加字段就等于加 token；本架构下加字段只加索引维度。

## 4. 技能引擎设计

### 4.1 模块划分

| 模块 | 职责 | 依赖 |
|---|---|---|
| `models.py` | `SkillMeta` / `Skill` / `RouteCandidate` / `RouteResult`，成本模型 | 标准库 |
| `parser.py` | `SKILL.md` 解析 + 元数据校验 | 标准库 |
| `tokenize.py` | 中英混合分词（3 种策略，供消融） | 标准库 |
| `bm25.py` | BM25 Okapi 检索通道 | 标准库 |
| `vectors.py` | TF-IDF 稀疏向量 + LSA 潜在语义 | 标准库（LSA 需 numpy） |
| `fusion.py` | RRF 多通道融合 | 标准库 |
| `registry.py` | 加载 / 校验 / 建索引 / 分字段检索 | 上述 |
| `router.py` | ★两阶段路由 + 依赖闭包编排 | 上述 |

### 4.2 分词策略（`tokenize.py`）

不引入 jieba。理由：① 额外依赖削弱可复现性；② 通用词典对安全术语切分不佳
（`越权`、`反序列化`、`Kerberoasting`）；③ 领域词典维护成本高。

**方案**：ASCII 词 + CJK 单字 + CJK 相邻二元组。

```
"水平越权 IDOR 测试"  →  ["水平","越权","idor","测","试","测试","平越","平","越","权"]
```

字符 bigram 在中文检索上效果接近分词，且天然覆盖未登录词与领域术语。
三种策略可切换（`hybrid` / `ascii_only` / `bigram_only`）作为消融自变量。

### 4.3 BM25 通道：分字段加权（`registry.py`）

**实测发现的缺陷**：把技能的全部字段拼成一段文本再做 BM25 会产生**文档长度偏置**。
本机语料中，5 个"伞状技能"（`src-6k-skill`、`pent3st`、`cve-yu2`、`secknowledge-skill`、
`vibe-pentest`）的 `description` 是数百字的中文长段落，而 103 个细粒度子技能的描述简短。
拼接式索引下，前者因词频累积几乎垄断 top-5。

**方案**：每个字段独立建 BM25 索引，逐字段**最大值归一化**后按权重求和。

```
score(d, q) = Σ_f  w_f · ( bm25_f(d, q) / max_d' bm25_f(d', q) )
```

归一化是必要的：不同字段的 IDF 量级不可比（`name` 字段的 IDF 天然远高于 `description`）。

| 字段 | 权重 |
|---|---:|
| `name` | 3.0 |
| `triggers` | 3.0 |
| `targets` | 2.0 |
| `description` | 1.0 |
| `domains` | 1.0 |
| `tools` | 1.0 |

保留拼接式索引（`scoring="flat"`）作为消融基线。

### 4.4 向量通道（`vectors.py`）

不使用 sentence-transformers / torch（Python 3.14 下无稳定轮子，且损害可复现性）。
采用两级：

1. **TF-IDF 稀疏向量**：sublinear tf + L2 归一化。与 BM25 的差异在于长度归一化方式，
   对短技能描述更公平。纯标准库。
2. **LSA 潜在语义**：TF-IDF 矩阵上做截断 SVD（`X ≈ UΣVᵀ`），文档向量取 `UΣ`，
   查询投影 `qᵀVΣ⁻¹`。可捕捉词面不重合的语义相近。仅需 numpy，百级文档下秒级完成。

神经嵌入模型可通过 `Embedder` 协议接入，作为消融的第四个通道，**但不是必需依赖**。

### 4.5 融合（`fusion.py`）

RRF（Cormack et al., SIGIR 2009）：`RRF(d) = Σ_c 1/(k + rank_c(d))`，`k=60`。

选 RRF 而非加权分数求和：BM25 得分无上界、余弦在 [-1,1]，量纲不可比，
归一化方式本身又是一个待调参的自由度。RRF 只用排名，无需归一化与调参。

### 4.6 ★两阶段路由器（`router.py`）

```
阶段一（召回，不注入上下文）
  查询 + 可选渗透阶段
    ├─ 分字段 BM25 ──┐
    └─ 向量通道  ────┴─▶ RRF 融合 ─▶ top-recall_n
                                       │
阶段二（按需加载）                      ▼
  仅注入 top-k 技能的元数据 + 正文 ─▶ Agent
```

**阶段先验**：若给定当前渗透阶段，与该阶段一致的技能获得 `phase_bonus` 加权奖励
（默认 0.004，可关闭），实现"分阶段动态路由"——侦察阶段完成后的技能集与
利用阶段不同，静态路由无法应对。

**依赖编排**：`dependency_closure()` 按 `requires` 展开拓扑序，并检测循环依赖。

**可解释性**：每个候选携带 `matched_fields` 与分字段归一化得分，前端直接渲染
"为什么召回这个技能"。实测输出形如 `命中 描述(1.00)`。

## 5. 成本模型（诚实版）

**朴素比较是错的。** 若直接比较「全量注入全部技能」与「只注入 top-k 正文」，
会得出**负节省**——因为真实技能正文长达数百行，5 个正文的开销远超 135 条元数据。
实测：该错误模型下 `token_saving_ratio = −0.99`。

**正确模型**：把成本拆为两项，并在**同等 k** 下对照（即假设基线也恰好选中同样
k 个技能——这对基线最有利，因而是保守比较）：

| 方案 | 元数据项 | 正文项 |
|---|---|---|
| 基线（agentskills.io 全量注入） | `N × meta` | `k × body` |
| 本课题（两阶段路由） | `k × meta` | `k × body` |

节省量恰为 **`(N − k) × meta`**，随技能库规模 `N` **线性增长**。
所以正确的论点是"**元数据开销从 O(N) 降到 O(k)**"，
而**不是**"总 token 一定更少"。

**实测（本机 125 个技能，查询「WordPress 管理员登录入口」，k=5）**：

| 项 | 基线 | 本课题 |
|---|---:|---:|
| 元数据 | 20,895 | 1,611 |
| 正文 | 40,038 | 40,038 |
| **合计** | **60,933** | **41,649** |
| 元数据项节省 | — | **92.3%** |
| 总开销节省 | — | 31.6% |

token 数由字符数按 1.6 字符/token 估算（中英混合语料经验系数），
**论文中须标注为估算方法**，正式实验应改用真实 tokenizer 计量。

## 6. 实测发现（截至当前语料）

> 可用 `backend/tools/probe_routing.py` 完整复现。

### 6.1 发现一：路由元数据完全缺失

`125/125` 个技能没有 `triggers`/`phase`/`domains`。它们只有 `name` + `description`。
**这直接证实了开题报告研究内容一的必要性——路由元数据必须被生成。**

### 6.2 发现二：中英跨语言路由鸿沟（核心问题）

本机语料是**双语异质**的：

| 技能群 | 数量 | 描述语言 | 举例 |
|---|---:|---|---|
| 伞状技能 | 5 | **中文长段落** | `src-6k-skill`、`pent3st`、`secknowledge-skill` |
| 细粒度子技能 | 103 | **英文** | `active-directory-kerberos-attacks`（"Use when targeting AD authentication via AS-REP roasting, Kerberoasting…"） |

探针实测（9 条查询，5 个期望技能片段）：

| 查询语言 | 命中期望技能 |
|---|---|
| **英文** | **3 / 3** |
| **中文** | **2 / 6** |

中文查询失败时，中文长描述的伞状技能几乎垄断 top-5；而中文的字面 token
**根本无法命中英文描述**。这不是实现缺陷，而是词面检索在双语异质语料上的固有失效模式。

**这是本课题最有价值的问题发现**，对应解法（待实现）：

1. **双语领域词典 + 查询扩展**：`越权 → BOLA/IDOR/authorization`、`后台 → admin panel`、
   `票据 → Kerberos ticket`、`域 → Active Directory`。离线、无 LLM 依赖。
2. **词典来源可自动化**：从技能 `name`/`description` 与 1610 份真实 SRC 报告中
   挖掘中英术语共现对，而非纯人工编写。

### 6.3 发现三：文档长度偏置

见 §4.3。已通过分字段 BM25 缓解。**效果须在 SkillRoute-Bench 上量化**（待实现）。

### 6.4 发现四：技能库存在同名冲突

8 组同名技能，全部是 `vibe-pentest/references/pentest_skills/` 中
**vendored 复制的 `hack-skills` 子技能**。注册表按 `name` 去重并**记录冲突而非静默覆盖**
（`LoadReport.duplicates`），保留先出现的 `hack-skills` 原件。

### 6.5 发现五：含中文的"无关"查询不会返回空结果

字符 bigram 会在词面上产生偶然重叠（如「内容」命中技能描述）。
这是词面检索的固有特性，不是缺陷——**真正的路由质量必须靠带标注真值的
SkillRoute-Bench 度量**，不能靠"看起来对不对"。

### 6.6 跨语言机制的消融结果（M3 已完成）

针对 §6.2 的跨语言鸿沟，实现了两种**互补且可独立开关**的机制（`lexicon.py`）：

| 机制 | 位置 | 开销 |
|---|---|---|
| **索引侧触发词富化** | 建索引时反查词典，把中文术语写入英文描述技能的 `triggers` 字段 | 一次付费，**查询期零开销**，结果可人工审阅 |
| **查询侧扩展** | 检索前把中文术语替换/追加为其英文等价词（最长匹配优先） | 每次查询一次词典查找 |

**消融实验**（14 条探针查询，10 中文 + 4 英文，`tools/probe_routing.py` 可复现）：

| 配置 | 中文命中 | 英文命中 | 总命中 | 召回失败 | 排序失败 | 阶段一 MRR |
|---|---:|---:|---:|---:|---:|---:|
| ① 基线（无跨语言支持） | 4/10 | 4/4 | 8/14 | **2** | 4 | 0.564 |
| ② 仅索引侧富化 | 7/10 | 4/4 | 11/14 | 0 | 3 | 0.615 |
| ③ 仅查询侧扩展 | 9/10 | 4/4 | 13/14 | 0 | 1 | 0.775 |
| ④ 两者都开 | 9/10 | 4/4 | 13/14 | 0 | 1 | 0.857 |
| ⑤ 人工词典（去挖掘层）+ 两机制 | **10/10** | 4/4 | **14/14** | 0 | **0** | 0.860 |

**结论**：
1. 中文命中率自 4/10 提升至 10/10，英文 4/4 **无退化**；
2. 跨语言机制**消除了全部召回失败**（2 → 0）——即鸿沟确实存在于检索层；
3. 但**代价是暴露了新的瓶颈**：见 §6.7。

### 6.7 发现六：瓶颈已从「召回」转移到「排序」，且探针集已饱和

这是本课题**最重要的方法学发现**，它决定了后续工作的方向。

**（1）召回不是瓶颈。** 逐条诊断（`ProbeOutcome.recall_failure` / `ranking_failure`）显示：
在启用跨语言机制后，**14 条查询全部成功召回**期望技能（阶段一名次 1～10），
**召回失败 0 例**。此前的"失败"是**排序失败**——技能进了候选池却没进 top-5。

> **这意味着继续增加检索通道或元数据字段不会改善结果**。
> 若不区分这两类失败，很容易误判方向、把工作量投在无收益的地方。

**（2）探针集已被打满（14/14），失去区分能力。** 最优配置在 14 条查询上全部命中，
说明该探针集**无法再区分方案优劣**——任何进一步的改进都无法在它上面体现。

> **这是必须构建 SkillRoute-Bench 的硬理由**，而非"为了好看"：
> 开发集饱和后，继续用它评估会产生"改进无效"的假象，或诱导研究者做
> 针对这 14 条查询的过拟合。

**（3）标签质量问题的自我暴露。** 首轮运行后的诊断发现，两条探针的**标注本身有误**：

| 探针 | 问题 |
|---|---|
| 中文·文件上传 | 期望只列了英文名片段，而语料中 `file-agent`（中文描述「负责文件类漏洞检测：…**任意文件上传**…」）才是正确答案——**"只按技能名标注"会系统性漏掉中文描述的正确答案** |
| 中文·WordPress 后台 | **语料中不存在任何 WordPress 相关技能**，该查询在当前技能库下**不可满足**，其"失败"毫无意义 |

两处修订已在 `app/eval/probes.py` 中**留痕记录**（含修订理由）。

> **这是最有说服力的"为什么需要正式基准"的论据**：单人标注的开发集出现了
> "不可满足的查询"与"命名偏见导致的漏标"两类错误。正式基准必须建立
> **公开的标注指南与复核机制**，否则任何基于它的结论都不可信。

#### 6.6.1 一处必须记录的自我纠错

第一轮实现中 `zh_triggers_for` 使用**子串匹配**，导致英文键 `id` 命中
`identifier` / `provide` 中的 `id`，把挖掘噪声「不限字段名」富化到大批技能上。
**该 bug 一度使富化成绩虚高**。

> **数值口径说明**：该 bug 的影响是在**修订前的标签集**上测得的
> （仅索引侧富化配置：有 bug 时中文 6/10，修复后 5/10）。标签修订后
> （§6.7）同一配置测得中文 7/10，数值不可与前者直接比较；
> 但**相对结论不变——bug 会抬高指标**。

**论文中应如实报告这一纠错**：它说明"指标提升"必须伴随实现审查，
否则容易把 bug 的副作用误记为方法的收益。

| 有 `targets` | **0** | 114 |
| 有 `triggers` | **0** | **125** |

覆盖层触及 125 个技能、填充 605 个字段，跳过 0 个（语料无任何已声明值）。

**2×2 消融（词典层 × 元数据层）**：

| 词典层 \ 元数据层 | 无元数据 | 有元数据 |
|---|---|---|
| 人工词典 | 14/14（中文 10/10，MRR 0.860） | 14/14（中文 10/10，MRR **0.869**） |
| 人工词典 + 挖掘 | 13/14（中文 9/10，MRR 0.857） | 14/14（中文 10/10，MRR 0.869） |

**诚实结论（元数据层的边际贡献很小）**：

1. 在人工词典组内，元数据层对**命中率**的边际贡献为 **0**，
   对 **MRR 仅 +0.009**（0.860 → 0.869）。
2. 在含挖掘层的组内，元数据层带来 +1 命中——但这是因为**它在补偿挖掘层引入的噪声**，
   而非元数据本身有用。**最优配置仍是"人工词典 + 无元数据"**（同为 14/14）。
3. **机制解释**：索引侧富化与元数据推断**都作用于 `triggers` 字段**，
   因此二者是**替代品而非互补品**。有了前者，后者的增量信息所剩无几。

> **这一负面结果必须写入论文**。它是对"补元数据就能提升路由"这一直觉假设的否证，
> 也说明**在设计阶段就分清各机制的作用面**（哪个字段、哪个阶段）比事后堆功能更重要。

**推断方法的可审计性**：每条推断都记录命中的关键词（`InferredMetadata.evidence`），
复核时只需检查"为什么给出这个标签"而非通读 125 个技能。
报告见 `docs/技能元数据生成报告.md`。

**仍需注意的局限**：规则是关键词匹配，无上下文理解能力。
正文仅取前 60 行（避免操作细节中的噪声词污染推断），
对同义改写与技术栈隐含描述无能为力。

### 6.9 SkillRoute-Bench v0：基准建成，并推翻了此前的三项设计假设

**基准规模**：86 条（计分 76 + **弃权用例 10**），中文 69 / 英文 17，全部 `source=hand`
（人工编写，无循环性风险）。标注规则见 `docs/SkillRoute-Bench-标注指南.md`。

#### 6.9.1 主干消融（每组只改变一个自变量）

| 配置 | R@1 | R@3 | R@5 | MRR |
|---|---:|---:|---:|---:|
| ① 基线（无跨语言，仅 BM25） | 0.513 | 0.632 | 0.658 | 0.579 |
| ② 仅索引侧富化 | 0.592 | 0.711 | 0.789 | 0.678 |
| **③ 仅查询侧扩展** | **0.684** | **0.789** | **0.829** | **0.748** |
| ④ 跨语言双机制 | 0.658 | 0.763 | 0.803 | 0.733 |
| ⑤ 加向量通道 + 等权 RRF | 0.526 | 0.724 | 0.763 | 0.635 |
| ⑥ 加向量通道（权重 0.3） | 0.618 | 0.763 | 0.816 | 0.706 |
| ⑦ 仅向量单通道 | 0.395 | 0.513 | 0.553 | 0.491 |
| ⑧ 拼接式 BM25（消融分字段） | 0.342 | 0.421 | 0.513 | 0.434 |

#### 6.9.2 三项被推翻的设计假设

**假设一：「混合检索（BM25 + 向量）一定优于单通道」——被推翻。**

⑤（等权 RRF 双通道）R@5 = 0.763，**低于**仅 BM25 的 ④（0.803），MRR 更从 0.733
跌到 0.635。原因是向量通道本身弱得多（⑦ 仅向量 R@5 仅 0.553），
等权融合把它当作与 BM25 同等可信的信号，**净效果是拖累**。
改为降权（⑥，向量权重 0.3）后 R@5 回升至 0.816，略高于单通道，但 MRR 仍更低（0.706）。

> **结论**：融合前必须先验证每个通道的独立质量；**"融合"不是免费的**。
> 若要保留向量通道，必须做权重标定而非等权。

**假设二：「分字段 BM25 是锦上添花」——被推翻，它是主力。**

⑧（拼接式）R@5 = 0.513 vs ④（分字段）R@5 = 0.803，**差距 0.290**——
单项设计的贡献远超跨语言机制（①→③ 为 +0.171）。
这印证了 §4.3 中「文档长度偏置」诊断的正确性：
不消除长度偏置，后续一切优化都建立在不可靠的排序之上。

**假设三：「两种跨语言机制互补，叠加应更好」——被推翻（与探针集结论一致）。**

③（仅查询侧扩展）0.829 > ④（两者都开）0.803。索引侧富化在查询侧扩展存在时
**略微有害**。机制解释：二者都作用于"把中文意图与技能词面接上"这一件事，
作用面重叠，而富化引入的噪声无法被查询扩展抵消。

> **最优配置为 ③：R@5 = 0.829，MRR = 0.748。**

#### 6.9.3 ★ 弃权能力为零，且 RRF 在原理上无法支持基于置信度的弃权

**实测**：10 条弃权用例（近义陷阱：含 MySQL 但属性能优化、含 Kubernetes 但属运维发布、
含 git 但属日常操作等）**全部被误路由，误路由率 100%**。

**第一版尝试**：用 RRF 融合得分做阈值。**失败，且是原理性失败**——
RRF 只用排名、丢弃分数大小，其得分恒等于 ``1/(k+rank)``，
**与匹配强度无关**。实测阈值从 0.004 扫到 0.016，弃权准确率**始终为 0**。

**第二版尝试**：改用尺度无关的 **IDF 加权查询词覆盖率**
（`BM25Index.weighted_coverage`）。信号确实存在但**分离度差**：

| 组 | 覆盖率均值 | 中位 | 范围 |
|---|---:|---:|---|
| 弃权用例（n=10） | 0.122 | 0.106 | 0.000 – 0.318 |
| 计分用例（n=76） | 0.236 | 0.180 | 0.000 – 1.000 |

**两组区间重叠宽度 0.318**，存在大片不可分区域。阈值扫描显示的权衡极差：
要达到弃权准确率 0.700，须误弃权 30/76 条正常查询（R@5 从 0.803 跌至 0.513）；
要达到 1.000，须误弃权 63/76 条。

> **诚实结论：简单的词面信号不足以支撑可靠弃权**。
> 原因是本质的——**正常查询也存在大量改写**（"优惠券只能领一次，用并发请求能不能
> 重复领取"↔`race-condition`），其词面覆盖率同样很低，与离题查询无法用单一阈值区分。
>
> 这是一条**有价值的负面结果**：它说明弃权需要独立的机制（如重排器打分、
> 多特征分类器、或显式的相关性判定），而不是在检索得分上加个阈值就能解决。
> 该问题列为后续工作，**不声称已解决**。

#### 6.9.4 分层报告

最优配置 ③ 的分层结果：

| 分层 | R@1 | R@5 | MRR |
|---|---:|---:|---:|
| 英文（n=16） | 0.875 | 0.938 | 0.895 |
| 中文（n=60） | 0.633 | 0.800 | 0.708 |

英文查询质量仍显著高于中文，说明跨语言鸿沟**只被缓解、未被消除**——
与 §6.6 的结论一致。

#### 6.6.2 双语词典的两层构成与挖掘层评估

| 层 | 规模 | 来源 | 评价 |
|---|---:|---|---|
| Tier 1 人工核心词典 | 144 个中文键 | 基于安全领域专业判断人工编写 | **驱动路由的主力**，精度高 |
| Tier 2 自动挖掘 | 并入 9 条（原始 479 对，≥2 次保留 69 对） | `tools/mine_lexicon.py` 从真实 SRC 报告与技能语料挖掘「中文（ENGLISH）」对照 | **当前未带来增益** |

**自动挖掘层实测结果**：对照实验显示，加入挖掘层后中文命中 **8/10 → 7/10**，
即**边际贡献为负**——因为挖掘层引入了「时间判断」「不限字段名」等句子片段噪声。

**语料与方法**：挖掘器读取 1484 个文件（DOCX 用标准库 `zipfile`+XML 抽取，
无需第三方依赖），从「中文（ENGLISH）」/「ENGLISH（中文）」对照写法中提取术语对，
再经可复现的过滤器剔除噪声（句子片段含功能词、报告状态词如「已修复」、
占位符如「待补」、文件名/路径如 `*.md`、`tmp/temp`）。

**诚实结论**：该挖掘方法**能挖到真术语**（`水平越权<->idor`、`垂直越权<->bfa`、
`反射型跨站脚本<->reflected cross-site scripting`），但**当前信噪比不足以直接并入生产词典**。
论文中应将其作为"方法可行但需人工复核"的结论报告，并给出噪声类型分类学
（句子片段 / 状态词 / 占位符 / 路径），这本身即有价值。

## 7. Agent 执行引擎设计（待实现）

### 7.1 执行循环

```
观察攻击图状态
  → 技能路由（两阶段，带 phase 先验）
  → 依赖编排（dependency_closure 补前置技能）
  → 工具调用（MCP）
  → 证据落盘（原始请求/响应）
  → 验证判据判定（Verifier 独立复核）
  → 更新攻击图
  → 终止判定（步数上限 / 状态无变化检测 / 目标达成）
```

### 7.2 角色分工

| 角色 | 职责 | 对应实现要点 |
|---|---|---|
| Orchestrator | 规划、技能路由、维护攻击图与队列 | 复用 `SkillRouter` |
| Executor | 执行技能操作序列、采集证据 | MCP 客户端 + 证据存储 |
| Verifier | **独立复核**发现，抑制误报 | 验证判据执行器（见下） |
| Reporter | 汇总结构化报告 | 模板 + 证据引用 |

### 7.3 验证判据（抑制误报的关键）

每个技能可在 frontmatter 声明 `verify:` 块，描述"什么算成功"。设计为**受限 DSL**，
仅允许可在沙箱中自动执行的操作子集：

```yaml
verify:
  - kind: http_diff            # 发送两个请求比较响应差异
    a: {method: GET, path: "/api/order/{id_a}"}
    b: {method: GET, path: "/api/order/{id_b}"}
    assert: both_200_and_different_owner
  - kind: status_change        # 未授权访问的判定
    request: {method: GET, path: "/admin/users"}
    assert: status_not_in: [401, 403]
```

**只有通过验证判据的候选才能升级为"发现"**，且必须附带可复现证据。

### 7.4 约束机制

- **作用域强制**：所有出站请求经统一出口，目标须在授权资产清单内，越界拒绝并告警；
- **风险审批**：`risk: high` 的技能默认挂起，需人在环路批准；
- **请求节流**：按目标维度限速；
- **攻击图收敛**：决策空间限定为"在攻击图上选择技能"，不在图上的资产不可达。
